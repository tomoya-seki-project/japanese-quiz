實現 UI-design.md 所需嘅 Django 後端改動

審查基準：UI branch，commit e70c82a｜報告日期：2026-09-30

呢份報告只列出為咗令 docs/reference/UI/UI-design.md 所描述嘅頁面流程、資料、權限、驗證、redirect、message、session 同狀態轉換真正運作，Django 後端要做嘅修改。

包括 Python views、forms、models、services、URLs、session、messages、queryset、權限、migration 同後端測試。
刻意不包括 Application HTML templates、CSS、JavaScript、SVG、圖片 asset、字體接入同純視覺 responsive 實作。
文件性質 呢份係實作前差異分析，唔代表以下 application code 已經修改。

結論摘要

6P0 必須先修會影響核心流程或資料正確性。
10P1 正式 UI 必做頁面流程、redirect、filter 或 toast 所需。
4P2 建議改善效能、結構同狀態一致性。
3Future scopeMC、學習紀錄、admin announcement。
最高風險：Quiz 題數狀態。 現有後端冇喺產生下一題之前強制檢查固定題數上限，而 skip 後呼叫下一題時亦刻意唔增加 quizzed_count。只改畫面會令固定題數、題號同 Summary 統計有機會唔一致，亦可以繞過前端直接要求額外題目。
現有 schema 已經支援大部分 v1.0.0 UI：Vocab、UserVocab、MCSense、Event、UserEvent、Feedback、QuizAttempt 等核心資料都存在。v1.0.0 嘅主要工作集中喺 view/form/service 行為，唔需要為一般 UI styling 大改 database。

P0：正式 UI 前必須修正

P0-1 統一 Quiz 進度計算並由 server 強制停止

現況：build_next_question_payload() 會直接揀下一題；只喺題庫空時結束。固定 10／20／30 題嘅上限冇喺 server 端檢查。Skip 流程傳入 is_skip=True 後，下一題亦唔會增加 quizzed_count。

要改：

  • 定義一個唯一進度來源，例如 attempted_count = correct_count + wrong_count + skipped_count，或者清楚重命名及維護 session counter。
  • Answer 同 Skip 完成後都算一題；建立下一題之前檢查 quiz_num，達上限直接回傳正常 Summary。
  • 題庫耗盡先標記 ended_early=True；達到 user 選擇題數係正常完成，唔應顯示提早結束原因。
  • 唔信任前端顯示嘅「次へ／結果へ」判斷；相關 POST endpoint 自己驗證目前進度。
  • Summary 總題數由三個結果 counter 計算，避免使用可能偏差嘅目前題號。

預計檔案：quiz/helper.py、quiz/views.py，必要時抽出 session state helper。

P0-2 重做「前回の設定を読み込む」後端契約

現況：use_last_setting 係 submit-time Boolean；一經選中，server 會忽略畫面目前值並即刻用 session 舊值開始 Quiz。呢個同 UI-design 要求「只載入欄位、仍可修改、之後先按開始」相反。

要改：

  • 移除 submit-time 覆蓋邏輯，開始 永遠驗證及保存當刻提交嘅設定。
  • GET Quiz Setting 時提供結構化嘅上一組設定同 has_previous_settings；可放 template context，或另設只讀 JSON endpoint。
  • 問題数 冇選擇時由 form/server 正規化成 -1，唔要求前端一定提交一個肉眼不可見嘅「無制限」選項。
  • 將 user 選擇設定同 runtime flag（例如 no-pool 後嘅 use_full_pool）分開，避免「載入上次設定」意外帶入一次性執行狀態。

預計檔案：quiz/forms.py、quiz/views.py；如分拆 session 結構，可新增 quiz session helper。

P0-3 Event detail 加入安全、冪等嘅「既読にする」POST

現況：Event list 已有批量設為已讀；Event detail 只有 GET。EventService.mark_as_read() 雖然存在，但未接駁 detail action。

要改：

  • 喺 detail view 實作 POST，或新增專用 action URL；必須由 URL 嘅 UserEvent.pk 定位。
  • queryset 必須同時限制 user=request.user，唔可以只靠 pk。
  • 用 transaction／條件 update 設定 is_read=True 同 read_at；已讀項目重複提交要安全成功。
  • 成功後 redirect 回同一 detail page並加入 既読にしました success message。

預計檔案：core/views.py、core/service/event.py，如果採用獨立 action 則包括 core/urls.py。

P0-4 修正 Logout result 導航

現況：UserLogoutView 設定 next_page=accounts:user_home，而 user_home 本身需要登入；logout 後會被再導去 login，未能穩定顯示獨立完成頁。

要改：令 POST logout 後 render／redirect 到真正嘅 logout result route，而唔係 redirect 去受保護嘅 HomeView。保留 CSRF-protected POST logout，唔改成 GET mutation。

預計檔案：accounts/views.py；視乎 route 設計可能調整 accounts/urls.py。

P0-5 所有 detail 返回連結保存並驗證 list context

現況：Vocab detail 同 UserVocab detail 已有 allowlisted next URL；Event detail 同 Feedback admin detail 未有同等後端處理。

要改：

  • 為 Event detail 建立安全 return URL，保留 event status filter 同 page。
  • 為 Feedback admin detail 建立安全 return URL，保留 status filter 同 page。
  • Feedback reply 返回 detail 時亦要保留原本 list context，或者由 detail URL/session 統一管理。
  • 繼續用 url_has_allowed_host_and_scheme()，唔可以直接 redirect 去未驗證嘅 query string。

預計檔案：core/views.py；建議抽出共用 safe-next helper，減少 dictionary/core 重複。

P0-6 補齊核心流程測試，先鎖定 server contract

現況：accounts/tests.py、dictionary/tests.py、quiz/tests.py 同 errorHandler/tests.py 幾乎係空白；現有主要測試集中喺 core/tests.py 嘅語言與 template smoke test。

要改：先為 Quiz 題數／skip、Event ownership、logout result、safe-next、雙提交 action 寫後端測試，再接正式 UI。否則 template/JS 改動會掩蓋 server state bug。

預計檔案：各 app tests.py，或拆成 tests/ package。

P1：按頁面完成正式 UI 所需後端改動

P1-1 補齊 success toast 對應嘅 Django messages

Toast 外觀係 frontend，但訊息來源及 redirect 後保留屬於 Django 後端責任。應只喺實際有成功 mutation 時加入 messages.success()。

流程現況後端改動
Login冇 success message登入、同步成功後加入訊息。
User vocab detail 保存redirect 同頁，但冇訊息值真係改變後加入訊息；no-op 可保持安靜。
Vocab create request已有 success/info保留統一文案即可。
Vocab update/delete request冇 success message建立申請後加入訊息；pending duplicate 用 info/warning。
Feedback create成功時冇訊息加入送出成功訊息。
User vocab 批量保存只寫 log實際 update count > 0 時加入訊息。
Event list 批量已讀只寫 log實際 update count > 0 時加入訊息。
Event detail 已讀流程未有由 P0-3 action 加入。
Admin Feedback reply已有 success保留但 redirect 目的地要改。

預計檔案：accounts/views.py、dictionary/views.py、core/views.py。

P1-2 Vocab create request 支援兩種成功目的地

現況：成功後固定返回 Homepage。UI-design 需要「申請→ホームへ」同「続けて→次の単語」兩個 submit intent。

要改：後端讀取並 allowlist 一個 action 值；兩個 action 都先完成同一套 validation、duplicate handling 同 transaction。home redirect Homepage；continue redirect 回 create page，靠 PRG 清空 form，同時保留 success message。未知 action 必須當 invalid request，唔接受任意 redirect target。

預計檔案：dictionary/views.py；可選擇喺 dictionary/forms.py 加隱藏 action field 作 validation。

P1-3 Vocab update/delete 成功後返回原本 detail

現況：兩個 view 都固定去 dictionary:vocab_home。UI-design 要返回被申請單語嘅 Vocab detail，並顯示 toast。

要改：用目標 vocab pk reverse detail URL；成功建立先發 success message。若已存在 pending request，使用清楚嘅 info/warning 狀態，唔可以假裝今次新建成功。

預計檔案：dictionary/views.py。

P1-4 Delete request 移除可見 checkbox 所綁定嘅後端要求

現況：VocabDeleteRequestForm 要求 confirm=True，否則 validation error。新規格係按紅色按鈕後由 modal 確認，頁面冇 checkbox。

要改：將 form 縮成只驗證可選理由；正式提交仍然係 CSRF-protected POST。Modal 係互動確認，唔應令 server 依賴一個 UI 已經唔存在嘅 checkbox。若保留 confirm token，必須係固定 allowlisted hidden action，而唔係當安全措施。

預計檔案：dictionary/forms.py、dictionary/views.py。

P1-5 Vocab detail 保證 MCSense 次序及完整資料

現況：MCSense model 同 reverse relation 已存在，但 model 冇 default ordering，detail queryset 亦冇預取。

要改：以 sense_no 穩定排序；可以加 Meta.ordering（會產生 migration state change）或喺 detail queryset 用 ordered Prefetch。同時 select_related('katakana_detail')、prefetch_related('categories', 'mc_senses')，確保頁面唔靠偶然 database order。

預計檔案：dictionary/views.py；若使用 model ordering，亦包括 dictionary/models.py 同 migration。

P1-6 User vocab detail 只提供規格需要嘅 last answer

現況：view 會為 last_answer 重新做逐字 DP 比較及產生圖片資料；新規格明確只顯示上次實際輸入文字，唔顯示逐字圖片或正誤比較。

要改：移除 detail view 嘅比較運算與 compared_result context；保留原始 last_answer。同時 queryset 預載 vocab、categories、katakana detail，保存 in_use 後加入 success message。

預計檔案：dictionary/views.py。

P1-7 Feedback admin list 改為每頁 5 筆及加入 status filter

現況：paginate_by=10，未有 queryset filter；UI-design 指定每頁 5 筆、預設 pending，選項包括 all/pending/replied/closed。

要改：

  • 改成每頁 5 筆。
  • allowlist status query parameter；缺少或非法值時使用 pending。
  • 切換 filter 時自然回到第 1 頁；pagination context 保留已驗證 filter。
  • queryset select_related('user', 'reply_by')，維持 -create_at 次序。

預計檔案：core/views.py；建議加入細小 filter form/class，避免手寫散落字串。

P1-8 Feedback reply redirect 回原本 detail

現況：成功 reply 後固定返 Homepage，而且 GET reply view 未集中載入／暴露目標 Feedback context。

要改：以 feedback_pk 取得目標、檢查未 closed、提供原 feedback 資料，成功後 reverse 到該 Feedback detail。Service 目前已有 transaction、row lock、closed guard 同 reply metadata 更新，可以保留。

預計檔案：core/views.py。

P1-9 日文狀態 label 保持單一可信來源

現況：site 已有 core/ui.py 日文 mapping，但 FeedbackStatus model choice labels 仍然係 English，Event type 亦有一個 English model label。公開/custom admin page 唔應直接跌返 English。

要改：將 site-facing label 集中為日文，並清楚區分 Django /admin/ 所需語言。可以沿用 core/ui.py 作公開 UI mapping；如果修改 TextChoices labels，要產生對應 migration state，並更新 label tests。

預計檔案：core/ui.py、core/models.py、core/templatetags/ui_labels.py、tests；視乎策略可能有 migration。

P1-10 Form requiredness 同 UI 規格保持一致

現有 create form 已將 meaning/level 設為 optional，category/reason/native Japanese 亦 optional；update form 繼承後令 meaning/level required，方向大致正確。正式接 UI 前仍要加測試鎖定：

  • Create：種類、単語、読み方必填；意味、JLPT、category、理由、katakana native Japanese 可選。
  • Update：word、kana、meaning、level 必填；type 不可修改；category、理由、native Japanese 可選。
  • Category 最多 3 個要繼續由 server 驗證，唔只靠 disabled button。
  • Katakana 專用欄位喺一般語彙提交時唔應保存，避免藏起咗嘅舊值污染 request。
  • Feedback/Admin announcement 必填內容由 Django form 驗證，唔只靠 browser attributes。

預計檔案：dictionary/forms.py、相關 service tests；admin announcement 見 Future-3。

P2：建議同頁面一齊整理

P2-1 List/detail queryset 預載關聯資料

Event list/detail、Feedback list/detail、Vocab detail 同 UserVocab detail 會顯示多個 foreign key／many-to-many 欄位。應按頁面使用 select_related／prefetch_related，避免正式 card/list render 後出現 N+1 query。

預計檔案：core/views.py、dictionary/views.py。

P2-2 批量 mutation 移入 service 並回傳 update count

User vocab 批量保存同 Event 批量已讀而家直接寫喺 view。建議移入 transaction-aware service，回傳 activated/deactivated/read count，由 view 決定 message。呢個會令權限限制、queryset scope 同測試更清楚。

預計檔案：dictionary/service/user_vocab_action.py、core/service/event.py、兩邊 views。

P2-3 限制 admin-only 全域 count query

unreply_feedback_count 目前對所有已登入 user 都查全站 pending feedback 數量。呢個 context 只對 admin 有用；應先檢查 superuser/staff 權限，普通 user 直接回 0，減少不必要 query，亦避免將管理資訊暴露到 template context。

預計檔案：core/context_processors.py。

P2-4 統一 POST/Redirect/GET 同 message 語意

對一般 Django form mutation，成功後一律 redirect；validation error 先原頁 render。對 Quiz AJAX mutation，固定 JSON schema：success、errors、main_html、input_panel_html、結束原因。咁可以避免新 UI 接入時每頁自行猜 response。

預計檔案：相關 views/helper；唔一定需要新 model。

Future scope：唔應混入 v1.0.0 必做

Future-1 Multiple Choice Quiz 完整後端

UI-design 已明確話 MC 唔係 v1.0.0 release blocker。現有 MCSense 只提供資料結構；目前 Quiz 流程仍以 kana answer 為主，而 check_mc_answer() 未形成可用嘅完整結果／weight／attempt contract。

將來需要獨立完成：

  • MC 題目選取與 sense 選取、四個答案生成及穩定隨機排序。
  • 每題 selected answer、已排除 distractors、hint count 同 attempt token 狀態。
  • 正解判定、weight、streak、last answer、QuizAttempt 結果資料同步更新。
  • 防止 client 偽造 hint／選項狀態，以及重複提交冪等處理。

預計檔案：quiz/models.py、migration、quiz/forms.py、quiz/service/quiz.py、quiz/views.py、tests。

Future-2 學習數據與最近十題

Homepage/User profile 目前按規格應先用「工事進行中」遮罩，所以 v1.0.0 唔需要即刻提供 backend data。真正開放時，現有 UserVocab 可以提供每個詞嘅累積資料，但「最近十題」同可靠 hint/答案歷史最好由 QuizAttempt 保存 snapshot。

建議將來加入：submitted answer、is_correct、hint count、question snapshot／sense、完成時間，並建立 user + processed time index。否則只靠 UserVocab.last_answer 無法重建十題歷史。

預計檔案：quiz/models.py、migration、answer/skip service、profile query service、tests。

Future-3 Admin event create page

UI-design 將頁面列為 future，但要求第一次整體 UI 預留共用 pattern。現時冇 custom event-create form/view/URL，而且 EventType 未有清楚嘅 system announcement 類型。

真正開發時需要：

  • 先決定可公開嘅 announcement type allowlist；如新增 enum value，要加 migration。
  • Superuser-only form/view/URL，種類、標題、內容全部 server-side required。
  • 確認 POST 後 transaction 建立 Event，再為全體目標 user 建立 UserEvent。
  • 大量 user 唔應逐個 get_or_create；改用分批 bulk_create(ignore_conflicts=True) 或等價安全方案。
  • 記錄 publisher、target count、event id；成功後 Homepage redirect + success message。
未決產品決定：第一版「種類」實際可選值未喺 UI-design 定義。唔應喺寫 code 時隨意重用 vocab 或 feedback_reply；要先定義 system announcement 類型。

預計檔案：core/models.py、migration、core/forms.py、core/views.py、core/urls.py、core/service/event.py、tests。

Feedback reply 內容關聯：UI-design 已接受目前限制：Feedback 本身只記錄 reply admin/time，reply 文字放喺獨立 Event，兩者冇 foreign key。因此「喺 Feedback detail 顯示歷次 reply 內容」唔列入今次必做；日後要做先新增關聯 model/migration。

現有後端可以直接保留嘅部分

  • 保留 全站 site UI 日文、Django admin 英文嘅 InterfaceLanguageMiddleware。
  • 保留 Registration、activation、resend activation email 基本流程同 resend cooldown。
  • 保留 Event list 每頁 5 筆、all/read/unread queryset 篩選基本行為。
  • 保留 Vocab list/User vocab list filtering、pagination query string 保存、目前頁批量提交嘅基本資料驗證方向。
  • 保留 Vocab/UserVocab detail 對 user ownership、active vocab 嘅 queryset 限制。
  • 保留 Category 最多 3 個嘅 server validation。
  • 保留 QuizAttempt token、row locking、duplicate answer/skip 防護、question unavailable 提早結束處理。
  • 保留 Kana DP comparison 同 answer graphic metadata 生成；正式結果頁仍然需要。
  • 保留 400/403/404/500 handlers，尤其 500 使用獨立 template render 嘅低依賴方向。
  • 保留 Feedback reply service 嘅 transaction、closed guard、reply metadata 同 Event 建立。

建議實作次序

  1. 先鎖定測試：Quiz 進度、skip、logout、Event ownership/safe POST、safe-next。
  2. 修正共用流程：messages、safe return URL、PRG、queryset preload。
  3. 完成 accounts/core：login/logout、Event detail、Feedback filter/reply。
  4. 完成 dictionary：雙提交、update/delete redirect、detail ordering、batch message。
  5. 完成 Quiz v1：上一組設定契約、無限制 default、固定題數、skip/summary consistency。
  6. 最後先接 frontend：用已固定嘅 endpoint、context 同 message contract 實作 HTML/CSS/JS。
  7. Future 獨立排期：admin announcement、學習歷史、MC Quiz，避免擴大 v1 scope。

後端驗收清單

  • 固定 10 題時，答題同 skip 合計第 10 題後一定進 Summary，直接打 Next endpoint 都唔會出第 11 題。
  • Summary 嘅總題數永遠等於正解 + 不正解 + skip。
  • 載入上次設定唔會開始 Quiz；修改載入值再提交時，以修改後值為準。
  • Event detail 只能修改目前登入 user 擁有嘅 UserEvent；重複標記已讀唔報錯。
  • Logout 後到獨立完成頁，唔會因 LoginRequired 再跳 login。
  • Create request 兩種 action 都只建立一次 request，並分別去正確目的地。
  • Update/delete 成功後返原 Vocab detail；pending duplicate 唔顯示虛假 success。
  • Feedback admin list 預設 pending、每頁 5 筆；filter + pagination context 保留。
  • Feedback reply 成功後返回原 detail；closed feedback 再 reply 被 server 阻止。
  • MCSense 永遠按 sense_no 顯示；詳細頁 query 數量唔隨 category/sense 數量線性上升。
  • 所有 mutation 使用 POST + CSRF；所有 next/return URL 經 host/scheme 驗證。
  • 普通 user context 唔包含全站 pending feedback count。
  • Registration、resend activation、Quiz form/filter 唔會誤發 success toast message。
