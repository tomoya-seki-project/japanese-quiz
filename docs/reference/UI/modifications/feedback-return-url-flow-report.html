Django Feedback 多層返回 URL

用同一條 Feedback list → detail → reply 流程，逐步比較兩種可行契約。方法 A 由 Reply 重建 Detail URL；方法 B 直接把完整上一頁 URL 傳落去。本文係設計與學習報告，唔代表所有示例 code 已套用到 project。

共同起點：List → Detail

Feedback list→ Feedback detail→ Feedback reply

List 將自己完整 URL 放入 Detail 嘅 next

<a href="{% url 'core:feedback_detail' pk=feedback.pk %}?next={{ request.get_full_path|urlencode }}">
    詳細を見る
</a>

例如目前 list 係第 2 頁並篩選 pending：

/core/feedback/list/?status=pending&page=2

進入 Detail 後，URL 會帶住呢條 list URL：

/core/feedback/detail/12?next=%2Fcore%2Ffeedback%2Flist%2F%3Fstatus%3Dpending%26page%3D2

Detail 嘅 get_return_url() 取得 List URL

class FeedbackDetailView(...):
    def get_return_url(self):
        next_url = self.request.GET.get("next")

        if next_url and url_has_allowed_host_and_scheme(
            next_url,
            allowed_hosts={self.request.get_host()},
            require_https=self.request.is_secure(),
        ):
            return next_url

        return reverse("core:feedback_list")

呢個 method 語意上等同較具體名稱 get_list_return_url()：Detail 返回時要去 List。兩套方法由下一步「Detail 將乜嘢傳畀 Reply」開始分開。

方法 A：Reply 收到 List URL，再重建 Detail URL

呢套方法令 Reply 嘅 next 直接保存 List URL。Reply 知道自己提交後應先返 Detail，所以要自己建立 Detail URL，再把 List URL 塞入新 Detail URL 嘅 next。

Detail → Reply：傳入 List URL

<a
    href="{% url 'core:feedback_reply' feedback_pk=feedback.pk %}?next={{ return_url|urlencode }}"
>
    返信
</a>

return_url 由 FeedbackDetailView.get_return_url() 提供，所以 Reply 收到：

Reply.next = /core/feedback/list/?status=pending&page=2

get_list_return_url() 讀取安全 List URL

def get_list_return_url(self):
    list_url = self.request.GET.get("next")

    if list_url and url_has_allowed_host_and_scheme(
        list_url,
        allowed_hosts={self.request.get_host()},
        require_https=self.request.is_secure(),
    ):
        return list_url

    return reverse("core:feedback_list")

呢一步只知道 Detail 將來應返回邊個 List，仲未建立 Reply 提交後要去嘅 Detail URL。

get_detail_url() 重建帶有回程資料嘅 Detail URL

from urllib.parse import urlencode
from django.urls import reverse


def get_detail_url(self):
    detail_url = reverse(
        "core:feedback_detail",
        kwargs={"pk": self.kwargs["feedback_pk"]},
    )
    query_string = urlencode({
        "next": self.get_list_return_url(),
    })

    return f"{detail_url}?{query_string}"
detail_url Reply 提交後首先返回嘅頁面：
/core/feedback/detail/12
query_string Detail 將來返回 List 所需嘅資料：
next=%2Fcore%2Ffeedback%2Flist%2F...
f"{detail_url}?{query_string}" 合成一條帶住 List 回程資料嘅 Detail URL：
/core/feedback/detail/12?next=%2Fcore%2Ffeedback%2Flist%2F...
關鍵：呢條 URL 只會先 redirect 去 Detail；問號後面嘅 next 係 Detail 日後按「一覧に戻る」先會使用。

get_success_url() 接駁 FormView

def get_success_url(self):
    return self.get_detail_url()

FormView.form_valid() 成功後會呼叫 get_success_url()。如果 Reply 頁另有「詳細に戻る」，get_context_data() 亦可以重用同一條 Detail URL：

def get_context_data(self, **kwargs):
    context = super().get_context_data(**kwargs)
    context["return_url"] = self.get_detail_url()
    return context
點解方法 A 需要 get_detail_url()：因為 Reply 收到嘅 next 只係 List URL，唔係完整 Detail URL。若只寫 return self.get_list_return_url()，提交後會直接跳過 Detail 返回 List。

方法 B：每一頁只接收「完整上一頁 URL」

呢套方法定義一條統一規則：每個頁面嘅 next 永遠係自己要返回嘅完整上一頁 URL。Reply 唔需要知道 Detail 再上一層係 List，亦唔需要重新建立 Detail URL。

Detail → Reply：傳入完整 Detail URL

<a
    href="{% url 'core:feedback_reply' feedback_pk=feedback.pk %}?next={{ request.get_full_path|urlencode }}"
>
    返信
</a>

request.get_full_path 包含目前 Detail path，同時保留 Detail 本身嘅 next=List URL：

Reply.next = /core/feedback/detail/12?next=/core/feedback/list/?status=pending&page=2

Reply 只需通用 get_return_url()

class FeedbackReplyView(...):
    def get_return_url(self):
        next_url = self.request.GET.get("next")

        if next_url and url_has_allowed_host_and_scheme(
            next_url,
            allowed_hosts={self.request.get_host()},
            require_https=self.request.is_secure(),
        ):
            return next_url

        return reverse(
            "core:feedback_detail",
            kwargs={"pk": self.kwargs["feedback_pk"]},
        )

讀到嘅已經係完整 Detail URL，所以唔使再拆 List URL，亦唔使再用 urlencode() 重建一層。

提交成功同返回按鈕重用同一條 URL

def get_success_url(self):
    return self.get_return_url()


def get_context_data(self, **kwargs):
    context = super().get_context_data(**kwargs)
    context["return_url"] = self.get_return_url()
    return context

Reply page 嘅 form 目前無寫 action：

<form method="POST">
    {% csrf_token %}
    {{ form.as_p }}
    <button type="submit">返信</button>
</form>

提交目的地仍然係目前 Reply URL，因此 query string 入面嘅 next 會繼續提供畀 POST request 使用。

返回鏈逐層解開

Reply.get_return_url()
└── 完整 Detail URL
    └── Detail.get_return_url()
        └── 完整 List URL

Reply 只理解 Reply → Detail；Detail 只理解 Detail → List。每個 View 都只管理自己嗰一步。

方法 B 唔需要 get_detail_url()：Detail URL 已由 Detail page 本身透過 request.get_full_path 完整傳畀 Reply。

再加 Dashboard：兩種方法都保留到更上層

Dashboard → List 時，List URL 可以先帶住 Dashboard URL：

<a href="{% url 'core:feedback_list' %}?next={{ request.get_full_path|urlencode }}">
    フィードバック一覧
</a>

List 負責自己返回 Dashboard：

class FeedbackListView(...):
    def get_dashboard_url(self):
        next_url = self.request.GET.get("next")

        if next_url and url_has_allowed_host_and_scheme(
            next_url,
            allowed_hosts={self.request.get_host()},
            require_https=self.request.is_secure(),
        ):
            return next_url

        return reverse("HomePage")

方法 A 嘅巢狀關係

Reply 收到 List URL
└── Reply 用 get_detail_url() 重建 Detail URL
    └── Detail.next = 完整 List URL
        └── List.next = Dashboard URL

方法 B 嘅巢狀關係

Reply.next = 完整 Detail URL
└── Detail.next = 完整 List URL
    └── List.next = Dashboard URL

兩套方法都可以保留 Dashboard；分別只係由邊一層負責建立 Detail URL。

目前 project 實際處於邊個位置

目前較接近方法 A，而且只完成到一半。
位置目前狀態代表意思
List → Detail 使用 request.get_full_path Detail 收到完整 List URL；已完成。
FeedbackDetailView.get_return_url() 驗證 next，fallback 去 List 功能等同方法 A 名稱較具體嘅 get_list_return_url()。
Detail → Reply 傳入 return_url return_url 係 List URL，所以 Reply 收到嘅係 List URL；屬於方法 A。
FeedbackReplyView 仍然以 HomePage 作 success_url 尚未加入方法 A 嘅重建 Detail URL，亦未改成方法 B 嘅完整上一頁契約。
Reply template 未有「詳細に戻る」link 如果加入返回 link，需要由 ReplyView 提供安全 Detail URL。
不可混用嘅位置：如果 Detail template 傳 return_url，Reply 收到嘅係 List URL，必須用方法 A；如果 Detail template 傳 request.get_full_path，Reply 收到嘅係 Detail URL，先可以用方法 B。只改 View 而唔同步改 template 會返回錯頁。

兩種方法比較

比較方法 A：重建 Detail URL方法 B：傳完整上一頁 URL
Reply 嘅 next List URL 完整 Detail URL
所需 methods get_list_return_url()、get_detail_url()、get_success_url() get_return_url()、get_success_url()
f"{detail_url}?{query_string}" 需要；用嚟重建帶 List 回程資料嘅 Detail URL 唔需要；完整 Detail URL 已由上一頁傳入
每層責任 Reply 需要知道 Detail 同 List 兩層 每個 View 只知道直接上一頁
追蹤 URL 建立位置 較明確；method 名直接指出 List／Detail 規則較統一；需要先理解巢狀完整 URL
增加更多頁面層級 可能增加更多專用 method 或重建邏輯 沿用「next = 完整上一頁 URL」
建議：目前流程用方法 B 較簡潔，因為你現有 List → Detail 已經使用 request.get_full_path。Detail → Reply 同樣傳完整目前 URL 後，三層就可遵守同一規則。不過方法 A 本身冇錯，亦保留喺本文作完整比較。
