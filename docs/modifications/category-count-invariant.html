Category 數量規則集中化與全寫入路徑保護

核心改修已完成

改修概要

原本「最多 3 個 category」只存在於一般 vocabulary request form，admin、審批 service、直接建立／更新 vocabulary 及 CSV import 並無共用嘅最終規則。今次將數量檢查抽成 iterable-safe validator，再按資料生命週期套用兩組界線：未審批 request 可以有 0–3 個 category；一旦 approve 或成為正式 vocabulary，就必須有 1–3 個。咁樣既保留 admin 拒絕資料不完整 request 嘅能力，亦阻止其他入口繞過 UI 寫入不合法資料。

主要修改重點

  • 以一個共用 validator 定義上限 3，並可由 caller 指定下限。
  • User request 及待審 admin form 接受 0–3；approve 與正式 vocabulary 強制 1–3。
  • Django admin 明確綁定兩個自訂 ModelForm，令欄位錯誤直接顯示喺頁面。
  • VocabActionService 成為 create／update 最終防線，CSV importer 自動繼承規則。
  • 系統檢查及 0、3、4 邊界 probe 通過；永久 regression tests 尚未補上。

修改目的 1：建立單一 category 數量規則

修改目的／理由

原本上限寫死喺 BaseVocabRequestForm.clean_categories()。呢個檢查只會喺該 form 執行，而且依賴傳入物件有 Django QuerySet 嘅 .count()。Service、admin form 或日後傳入普通 list／generator 時，都無法直接重用。

受影響檔案與責任

  • dictionary/validators.py：保存共用常數、數量判斷及一致嘅 ValidationError。
  • dictionary/forms.py：一般 request form 改為呼叫共用 validator，同時保留原有日文 UI 訊息。

修改前

dictionary/forms.py（HEAD）

def clean_categories(self):
    categories = self.cleaned_data["categories"]
    if categories.count() > 3:
        raise forms.ValidationError(
            "カテゴリーは3つまで選択できます。"
        )
    return categories

規則只保護使用呢個 form 嘅入口；數字 3、檢查方法同 UI 訊息亦綁埋一齊。

修改後

dictionary/validators.py（目前第 3–18 行）

MAX_VOCAB_CATEGORIES = 3

def validate_category_count(
    categories,
    *,
    min_count=0,
    max_count=MAX_VOCAB_CATEGORIES,
):
    categories_list = list(categories)
    categories_count = len(categories_list)

    if categories_count < min_count:
        raise ValidationError(
            f"Select at least {min_count} category."
        )
    if categories_count > max_count:
        raise ValidationError(
            f"Select no more than {max_count} categories."
        )

    return categories_list

前後差異與運作解釋

Validator 先用 list(categories) 將 QuerySet、list 或一次性 generator 正規化，再以 len() 計數。合法時回傳同一份 materialized list，caller 可以直接交畀 ManyRelatedManager.set()，唔需要再次 evaluate QuerySet，亦唔會遇到 generator 已經被消耗嘅問題。

min_count 同 max_count 係 keyword-only parameters；caller 必須寫出參數名，令 min_count=0 或 min_count=1 嘅業務意思更明確。上限則集中由 MAX_VOCAB_CATEGORIES 控制。

一般 request form 捕捉共用 error，再轉成原有日文訊息。換言之，domain rule 集中咗，但 user-facing 語言仍然由 presentation layer 負責。

新使用技術

  • Iterable normalization：先 materialize 成 list，統一處理 QuerySet、list 及 generator。
  • Keyword-only arguments：* 後嘅參數必須具名傳入，降低上下限填反嘅風險。
  • Validator 回傳 normalized value：檢查與後續寫入共用同一份資料。

修改目的 2：按 request 生命週期使用不同下限

修改目的／理由

「待審 request」同「正式 vocabulary」唔應該用完全相同嘅下限。Request 允許 category 暫時為空，admin 先可以打開不完整資料並選擇 reject；但 approve 之後資料會進入正式題庫，所以審批嗰一刻必須至少有 1 個 category。

受影響檔案與責任

  • dictionary/forms.py：新增兩個 admin ModelForm，分別檢查 proposed_categories 及正式 categories。
  • dictionary/admin.py：透過 ModelAdmin.form 將自訂 forms 接入 add／change pages。
  • dictionary/service/vocab_request.py：approve 前以 1–3 規則驗證 proposed categories，並將錯誤加入原有 aggregated error dictionary。

前後差異與運作解釋

入口／狀態允許數量點解
User 提交／修改 request0–3沿用 pending request 可暫時缺資料嘅設計。
Admin 編輯 pending request0–3如果強制最少 1 個，admin 連零 category request 都無法儲存／reject。
Admin approve request1–3正式建立／更新前收緊 invariant。
Admin 直接編輯正式 Vocab1–3避免 admin page 寫入正式但無分類或分類過多嘅資料。

clean_<fieldname>() 係 Django form 嘅欄位級 validation hook。當 admin 將自訂 ModelForm 指派到 ModelAdmin.form，add／change page submit 時就會執行相應 clean method，error 會留喺對應 category 欄位。

Approval service 保留原有「收集全部錯誤後一次 raise」流程；category validator 嘅 error.messages 被放入 errors["proposed_categories"]，所以佢可以同 word、kana、meaning 等缺漏一齊回報。

新使用技術

  • Django ModelForm.clean_<fieldname>()：對指定 admin form field 做欄位級 validation。
  • Django ModelAdmin.form：覆寫 admin 預設動態 form，接入自訂 validation。
  • ValidationError.messages：保留一個欄位可能包含多個訊息嘅 list shape。

修改目的 3：保護最終寫入與 CSV import

修改目的／理由

只喺 form 驗證並不足夠：service 可以被 admin approval、management command 或日後其他程式入口直接呼叫。真正需要長期成立嘅 invariant，必須喺最接近正式資料寫入嘅 service 再檢查一次。

受影響檔案與責任

  • dictionary/service/vocab_action.py：所有正式 vocabulary create／update 在 transaction 及 model save 之前先驗證 1–3 個 category。
  • dictionary/management/commands/import_vocab.py：本次無修改；現有 importer 經由 VocabActionService.create_vocab() 自動取得相同防線。

修改前

dictionary/service/vocab_action.py（HEAD）

with transaction.atomic():
    vocab = Vocab(...)
    vocab.full_clean()
    vocab.save()
    vocab.categories.set(vocab_data["categories"])

full_clean() 發生喺 object save 前，而 many-to-many categories 係 object save 後先用 .set() 寫入；因此呢段本身無檢查 category 數量。

修改後

dictionary/service/vocab_action.py（目前第 24–41、55–70 行）

categories_list = validate_category_count(
    vocab_data["categories"],
    min_count=1,
)

with transaction.atomic():
    vocab = Vocab(...)
    vocab.full_clean()
    vocab.save()
    vocab.categories.set(categories_list)

update_vocab() 使用同一個 pattern，兩條正式寫入路徑一致。

前後差異與運作解釋

Web request／Admin approval／CSV import／其他 caller
                         ↓
            VocabActionService.create_vocab()
                         或
            VocabActionService.update_vocab()
                         ↓
        validate_category_count(min_count=1)
              ↙ 合法                 ↘ 不合法
     開 transaction 及寫入       raise ValidationError
                                 （尚未寫 database）

Validator 喺 transaction.atomic() 之前執行。0 個或 4 個 categories 會即時 raise，連 Vocab.save() 都未開始。合法時，已 materialize 嘅 categories_list 直接交畀 related manager 嘅 .set()。

CSV importer 目前最多讀取 category1 至 category3，並會先拒絕不存在嘅 category 名稱。即使三個欄位最後搵唔到任何有效 category，service 嘅下限檢查仍會阻止建立正式 vocabulary；既有 except ValidationError 會將該 row 記錄為失敗並繼續下一行。

新使用技術

  • Service-layer invariant：將資料完整性檢查放到所有正式寫入必經嘅 application service。
  • Fail fast：先驗證再開始 transaction，避免建立部分 object 或進行無必要 database work。
  • Many-to-many RelatedManager.set()：正式 object 儲存後，以已驗證 iterable 取代整組關係。

已知限制／未驗證事項

未有永久 regression tests：目前邊界測試係一次性 shell probe，未放入 tests.py。日後改 validator、forms 或 service 時，CI 唔會自動重跑 0／1／3／4 呢組邊界。
  • 未以 browser 實際提交兩個 admin pages，確認 error 顯示位置及文案；今次只驗證 Python validation 行為與 admin form wiring。
  • Admin forms 目前直接顯示 validator 嘅英文訊息；一般 user request form 則保留日文訊息。若 admin UI 亦要統一日文，需要另行處理 presentation 文案。
  • 規則係 application-level validation，並非 database constraint。繞過 Django service、直接操作 many-to-many through table 嘅程式仍可破壞 invariant。
  • min_count／max_count 係內部 caller contract，validator 本身無額外拒絕負數或 min_count > max_count 呢類錯誤設定。
