Django Production Settings Hardening

設定模式已完成；實際部署待處理

修改概要

原本嘅Django quick-start設定將SECRET_KEY、DEBUG=True同空白ALLOWED_HOSTS直接寫死，適合本機起步，但唔能夠安全地切換到production。改修後，敏感值、environment switch、host／origin allowlist同HSTS時間全部由environment variables提供；當DEBUG=False時，Django先自動啟用HTTPS redirect同secure cookies。本機仍然可以用HTTP runserver，而production可以使用另一組environment values，毋須再改application source。

主要修改重點

  • SECRET_KEY改成required environment variable，漏設會立即停止啟動。
  • DEBUG、ALLOWED_HOSTS同CSRF_TRUSTED_ORIGINS支援文字環境變數解析。
  • HTTPS redirect、secure session／CSRF cookies同HSTS只會喺production branch啟用。
  • 同一份settings.py可配合development同production兩組設定；production-style runtime assertions已通過。

修改目的1：移除寫死嘅secret同debug mode

修改目的／理由

Production secret唔應該進入Git history，而production亦唔可以開啟會顯示traceback、local variables同settings資料嘅debug page。設定改成由外部environment提供後，同一份source code先可以安全地喺不同環境使用。

受影響檔案與責任

  • config/settings.py:27-32：要求SECRET_KEY存在，並將文字形式嘅DEBUG轉成Python boolean。
  • .env.example:17-18：公開所需key名稱同development預設形狀，但唔保存任何真正secret。
  • .env：保存本機真正值；已由Git ignore，內容完全排除於報告。

修改前

config/settings.py｜HEAD 10f6dd2；literal已遮蔽

SECRET_KEY = "<committed-development-key>"

DEBUG = True

修改後

config/settings.py:27-32

SECRET_KEY = os.environ["SECRET_KEY"]

DEBUG = os.getenv(
    "DEBUG",
    "False",
).strip().lower() == "true"

前後差異與運作解釋

os.environ["SECRET_KEY"]係required lookup：如果環境漏設，application啟動時會立即拋出錯誤，避免靜默使用假secret。舊key已經存在Git history，所以只可當development key，production必須產生一個未曾提交、亦唔同其他project共用嘅隨機值。

Environment variable永遠以字串讀入。bool("False")其實係True，所以要先strip()、再lower()，最後明確比較"true"。預設值設為False，代表漏設時採用較安全嘅production方向，而唔係意外打開debug。

新使用技術

Python os.environ／os.getenv()：前者適合必須存在嘅secret，後者適合有合理預設值嘅environment switch。呢個修改無新增dependency，而係沿用標準庫os。

python-dotenv 1.2.3：load_dotenv(BASE_DIR / ".env")已由早前PostgreSQL修改建立；今次重用佢將本機.env載入process environment。Production可以由hosting平台直接提供environment values，毋須依賴上傳本機檔案。

修改目的2：建立host同CSRF origin allowlist

修改目的／理由

DEBUG=False時，Django需要明確知道可以服務邊啲Host header；HTTPS POST亦要知道邊啲origin可信。Development同production使用不同domain，因此兩組allowlist都要由environment提供。

受影響檔案與責任

  • config/settings.py:34-47：將comma-separated environment string拆成list，並移除空格同空項目。
  • .env.example:19-20：示範本機host同origin格式。
  • 未追蹤.env：目前啟用development profile，另以comment保留production profile參考；同一時間只應啟用一組同名key。

修改前

config/settings.py｜HEAD 10f6dd2

ALLOWED_HOSTS = []

# CSRF_TRUSTED_ORIGINS 未設定

修改後

config/settings.py:34-47

ALLOWED_HOSTS = [
    host.strip()
    for host in os.getenv("ALLOWED_HOSTS", "").split(",")
    if host.strip()
]

CSRF_TRUSTED_ORIGINS = [
    origin.strip()
    for origin in os.getenv(
        "CSRF_TRUSTED_ORIGINS",
        "",
    ).split(",")
    if origin.strip()
]

前後差異與運作解釋

ALLOWED_HOSTS填host name，唔包含scheme、path或尾斜線，例如app.example.com。CSRF_TRUSTED_ORIGINS填origin，必須包含scheme，例如https://app.example.com。兩者唔係同一份資料：前者保護Host header boundary，後者處理跨origin unsafe request嘅CSRF信任。

split(",")將一個environment string拆開；list comprehension逐項strip()並用if host.strip()排除空值。呢個pattern可以重用於其他comma-separated設定，但只適合值本身唔會包含comma嘅情況。

新使用技術

Django host validation：Django會以ALLOWED_HOSTS驗證經request.get_host()取得嘅Host header；精確列出domain比使用*更安全。

Django CSRF trusted origins：HTTPS request帶有Origin時，CSRF middleware會檢查來源；只有確實需要信任嘅scheme + host應該加入list。

修改目的3：只喺production強制HTTPS

修改目的／理由

Production登入、session同activation flow需要全站HTTPS；但普通runserver只提供HTTP。如果secure settings無條件啟用，本機會被redirect去無法提供嘅https://localhost，session同POST亦唔能夠正常運作。因此安全設定以if not DEBUG作environment boundary。

受影響檔案與責任

  • config/settings.py:50-59：production啟用HTTPS redirect、secure cookies同HSTS。
  • .env.example:21：development HSTS為0；真正production environment先由較短時間開始。

修改前

config/settings.py｜HEAD 10f6dd2

# 無production-only HTTPS settings

修改後

config/settings.py:50-59

if not DEBUG:
    SECURE_SSL_REDIRECT = True
    SESSION_COOKIE_SECURE = True
    CSRF_COOKIE_SECURE = True

    SECURE_HSTS_SECONDS = int(
        os.getenv("SECURE_HSTS_SECONDS", "3600")
    )
    SECURE_HSTS_INCLUDE_SUBDOMAINS = False
    SECURE_HSTS_PRELOAD = False

前後差異與運作解釋

SECURE_SSL_REDIRECT將HTTP request導向HTTPS；兩個*_COOKIE_SECURE令browser只經HTTPS送出session同CSRF cookies。SECURE_HSTS_SECONDS會要求browser喺指定時間內直接使用HTTPS，因此只應喺certificate、proxy同redirect全部確認正常後由短時間開始。

SECURE_HSTS_INCLUDE_SUBDOMAINS=False同SECURE_HSTS_PRELOAD=False係刻意保守選擇。打開前要確認相關subdomains全部永久支援HTTPS，亦要理解browser preload list係長期承諾；唔應只為清除deploy check warning而開。

新使用技術

Django SecurityMiddleware：Project本身已載入middleware；今次開始透過security settings使用佢嘅HTTPS redirect同HSTS response header能力。Secure cookies則由session同CSRF設定控制browser傳送條件。

Production profile
