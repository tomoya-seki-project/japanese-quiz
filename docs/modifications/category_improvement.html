Category Improvement：由單一分類遷移至多分類

按原報告：核心改修已完成

改修概要

Dictionary 原本以 CharField 同 TextChoices 保存單一 category，無法表達一個詞彙同時屬於多個語義場景。改修後新增 Category master data，將 Vocab 同 VocabRequest 轉為 ManyToMany 關係，並同步更新 migration、request/approval service、admin、CSV import 同搜尋入口。

主要修改重點

  • Category 由硬編碼 enum 改成可管理嘅 database master data。
  • Vocab.categories 同 VocabRequest.proposed_categories 成為唯一 category 資料來源。
  • Create、update、restore request 都會保存 proposed category snapshot。
  • Form 允許 0–3 個選擇，approval 要求至少 1 個；database 未全域保證 1–3 個。
  • Admin、CSV import、vocab list 同 user vocab list 已改用 M2M 資料。

修改目的 1：建立可擴展嘅多分類資料模型

修改目的／理由

單一字串 category 無法表達多重語義，固定 TextChoices 亦令 category master data 難以獨立管理。

受影響檔案與責任

  • dictionary/models.py
  • dictionary/migrations/0020–0022
  • resource/categories.csv
  • dictionary/management/commands/setup_categories.py

修改前狀態

Vocab.category 同 VocabRequest.proposed_category 各自保存一個字串，選項由 VocabCategory TextChoices 寫死。

修改後狀態

Category 成為 master table；Vocab.categories 同 VocabRequest.proposed_categories 以 ManyToMany 保存多個關係，舊欄位及 enum 被移除。

前後差異與運作解釋

展開原報告嘅詳細技術內容與 code evidence

目的

今次改動係將 dictionary app原本單一category設計，改成一個vocab可以擁有多個categories。現時user request form容許提交0至3個categories，方便管理員補充資料；approve時則要求最少有1個。Database model本身並無全域強制最多3個。

舊設計：

  • Vocab.category：單一 CharField
  • VocabRequest.proposed_category：單一 proposed category
  • choices 由 VocabCategory TextChoices 固定寫死

新設計：

  • Category model 管理 category master data
  • Vocab.categories 使用 ManyToManyField
  • VocabRequest.proposed_categories 使用 ManyToManyField
  • Vocab create / update / restore request 都保存 proposed categories snapshot
  • Vocab list / user vocab list search 改用 M2M categories filter

設計原因

單一 category 太限制 vocab 分類。部分字可以同時屬於多個語義場景，例如：

  • 食事・料理
  • 日常生活
  • 文化・娯楽

現時user request form以最多三個categories作產品層限制，可以保持資料彈性，同時避免一般提交包含過多category，令quiz／filter／admin review變得混亂。呢個上限唔係M2M data model本身嘅invariant，其他寫入入口需要自行執行相同validation先會得到一致規則。

修改目的 2：令 request 同 approval 流程完整傳遞 categories

修改目的／理由

資料模型轉成 M2M 後，create、update、restore、review 同 approve 都要保存及驗證同一組 proposed categories。

受影響檔案與責任

  • dictionary/forms.py
  • dictionary/views.py
  • dictionary/service/vocab_request.py
  • dictionary/service/vocab_action.py

修改前狀態

Forms、initial data 同 services 只處理 category／proposed_category 單一值。

修改後狀態

ModelMultipleChoiceField 接收多選；request 保存 snapshot；approval 驗證最少一項，再由 vocab action 於主物件保存後設定 M2M。

已知限制／未驗證事項

1. Existing data migration

如果 production / long-lived database 已有舊 Vocab.category data，要喺 drop column 前做 data migration，將舊 category 搬去 M2M table。

今次 development flow 已經直接清走舊欄位。

2. Category count rule

目前user request form嘅欄位係optional，所以提交時可以選0至3個categories；form只執行最多3個嘅限制。Review／approve service會要求最少有1個category，但無執行最多3個限制。ManyToManyField及database亦無內建呢個cardinality constraint。

如果產品規則真係要求所有已批准vocab一律只有1至3個categories，就要喺所有寫入入口統一執行限制，例如集中喺service validation，並為admin、API同management command補相同保護。單靠一般user form不足以形成全系統invariant。

3. Query performance

M2M filter 會 join through table。

目前資料量細，無問題。之後如果 vocab / user_vocab 數量大，可以再考慮：

  • index
  • prefetch
  • query optimization

4. UI display

目前 list item 未必完整顯示 categories。

如果之後需要，可以喺 vocab list / user vocab list 加 category badges。
