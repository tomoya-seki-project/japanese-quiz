用現時 project 實作拆解一次 POST 點樣由按鈕，經 Django Admin form lifecycle，再落到 service transaction。重點唔係背 method 名，而係知道每一層負責咩。

最易混淆位：get_form() 只係設定「Reject 時必須填 note」呢條規則；真正判斷空唔空係之後嘅 form.is_valid()。而 response_change() 係 form 成功保存後先到。

完整時序圖

虛線分支表示同一次 POST 只會行其中一條路。Reject note 空白會喺 form validation 截停；成功路線先會去 service。

逐步拆解

UICustom button 將意圖放入 POST

兩個 button submit 同一張 form。按 Approve 時 POST 有 _approve=1；按 Reject 時有 _reject=1。按鈕唔會直接呼叫 service。

鎖get_queryset() 取得目標 request

只要係 approve/reject POST，queryset 加 select_for_update()。Django Admin 嘅 change-form POST 本身位於 transaction 之內，所以讀取 object 時可以提早鎖 row。

Formget_readonly_fields() 決定可唔可以編輯

Pending request 依設定開放欄位；已 reviewed request 將 concrete model fields 變 readonly，避免舊頁面再改記錄。

Formget_form() 組成本次 Form class

如果 POST 有 _reject，將 review_note.required 設為 True。Approve 冇呢個條件，所以 note 仍可空白。

Formform.is_valid() 真正執行驗證

Reject note 空白會產生 required error，重新 render change page。後面嘅保存、審批、事件通知全部唔會發生。

Adminsave_model() 保存 form data

表單有效先會到呢度。Pending request 會 call super().save_model() 保存，例如剛填好嘅 review_note；reviewed request 就被擋住。Many-to-many data 會由後續 save-related 階段處理。

分流response_change() 讀取按鈕

佢檢查係 approve 定 reject、確認 change permission、呼叫相應 service，最後用 message_user() 顯示結果並 redirect。普通 Save 則交返 super()。

DomainService 做真正審批

Service 自己開 transaction.atomic()、重新 query 並 lock row、再次檢查 status。Approve 再按 request type 改 vocab；Reject 只改 request 狀態。成功後保存 reviewer，並以 review note 作通知內容。

Approve 與 Reject 實際分支

Approve

  1. review_note 可以空白。
  2. form valid，先保存 admin 改動。
  3. response_change() 檢查 vocab type 及 permission。
  4. service 根據 CREATE / UPDATE / RESTORE / DELETE 改 vocab。
  5. request 變 APPROVED，保存 reviewer，建立結果 event。

Reject

  1. get_form() 將 review_note 變 required。
  2. 空白就 form invalid，流程立即停止。
  3. 有效 note 先由 save_model() 保存。
  4. response_change() 檢查 permission，再 call reject service。
  5. request 變 REJECTED，保存 reviewer，note 放入結果 event。

點解要鎖兩次？

表面上 Admin get_queryset() 同 service 都有 select_for_update()，其實責任範圍唔同：

  • Admin early lock：保護由 change form 讀 object、保存表單到 action 分流呢段 admin lifecycle。
  • Service self-lock：保證任何 caller 就算唔係 Django Admin，都必須經過 row lock 同最新 pending check。

Lock 唔等於規則。Lock 只令兩個 transaction 排隊。第二個 reviewer 等第一個完成後，仍要靠重新讀取 status，先知道唔可以再處理。
