Quiz answer_compare() 效能改善

兩套方案：Top-down recursion + memoization 同 Bottom-up dynamic programming + backpointer

根據 2026-09-01 working tree；只係設計說明，未修改 quiz implementation。

1. 結論先講

方案 A

Memoization

最少改動、較容易保留目前輸出，適合作為快速修正。時間複雜度由指數級降至 O(mn)，但 recursive call、完整 result list 複製同 cache memory 仍存在。

方案 B

Bottom-up DP

正式建議。每格只保存 score、operation 同下一步位置，最後一次過重建結果。同樣係 O(mn)，控制流程、記憶體用途同 performance testing 都比較清楚。

推薦：如果下一步只想安全修止血，用 A；如果你準備正式重整呢段核心演算法，直接做 B，避免短期修完之後再重寫一次。

問題唔係有三種選擇，而係同一個 state 會經唔同路徑重覆計。例如 (2, 2) 可以由較早嘅 WRONG、MISSING+EXTRA、EXTRA+MISSING 到達。現有 recursion 唔記得自己計過，所以成棵 tree 不斷重算。

3. 現有選擇規則必須保留

呢段 code 唔係普通 Levenshtein distance；佢除咗搵最低 cost，仲會喺同分時揀較有教學價值嘅 alignment：

key = (
    cost,                         # 越少越好
    -match_count,                 # 同 cost 時，MATCH 越多越好
    -non_normal_wrong_count,      # 再同分時，特殊錯誤分類越多越優先
)

non_normal_wrong_count 包括 DAKUTEN、HANDAKUTEN、SMALL_KANA，令「が → か」可以呈現為濁音錯誤，而唔係被拆成難理解嘅 missing/extra。

所以無論 A 或 B，都唔可以只保存一個 integer distance；每個 state 最少要比較以下 score：

Score(cost, match_count, non_normal_wrong_count)
ranking = (cost, -match_count, -non_normal_wrong_count)

4. 方案 A：Top-down recursion + memoization

理論

保持「由目前位置問：餘下字串最佳答案係乜」嘅 recursive 思維，但第一次計完 (i, j) 後存入 cache。下次再到同一 state，直接取結果，唔再展開三條 branches。

compare(i,j)
→
Cache 有？
有：直接 return
／
冇：計三條 path
選最佳再 cache

建議結構

將 answer strings 放喺外層，cached function 只接收兩個 integer positions，cache key 就會簡單而穩定：

def answer_compare(correct_answer, user_answer):
    @lru_cache(maxsize=None)
    def solve(i, j):
        if i == len(correct_answer) and j == len(user_answer):
            return Score(0, 0, 0), ()

        if i == len(correct_answer):
            return extra_tail(j)

        if j == len(user_answer):
            return missing_tail(i)

        if correct_answer[i] == user_answer[j]:
            next_score, next_result = solve(i + 1, j + 1)
            return add_match(next_score), (MATCH,) + next_result

        candidates = (
            add_wrong(solve(i + 1, j + 1), i, j),
            add_missing(solve(i + 1, j), i),
            add_extra(solve(i, j + 1), j),
        )
        return min(candidates, key=ranking_key)

    score, result = solve(0, 0)
    return result_as_current_contract(score, result)

上面係設計 pseudocode，重點係 cache 只屬於今次 function call；唔好將帶住某一對答案嘅 cache 長期放喺 class/global scope。

正式執行流程

  1. compare_kana_answer() normalize None 成空字串。
  2. 建立 request-local cached solve(i,j)。
  3. 遇到 base case 直接產生 remaining MISSING／EXTRA。
  4. 遇到 MATCH，只計 solve(i+1,j+1)。
  5. 遇到 mismatch，取三個 child states；child 如已 cache 就直接重用。
  6. 用現有 ranking key 選最佳 candidate。
  7. solve(0,0) 回傳同目前完全相同嘅 dictionary contract，後面 gen_answer_image() 毋須改。

優點、代價及陷阱

面向評估
改動量低；最容易沿用現有 recursion、base cases 同 output。
時間O(mn)，每個 (i,j) 最多真正計一次。
空間基本 state O(mn)，但如果每個 cached state 都保存完整 result tuple/list，實際複製量可高於 O(mn)。
風險Mutable list 被 caller 修改會污染 cached result；應使用 immutable tuple，輸出前先轉 list。
可讀性同現有寫法最接近，但 recursion、cache、result reconstruction 混合埋一齊。

5. 方案 B：Bottom-up DP + backpointer

理論

建立一個 (m+1) × (n+1) table。dp[i][j] 表示「由 correct[i:] 同 answer[j:] 開始，最佳結果嘅 score」。由右下角 base case 倒轉填到左上角，確保計一格之前，佢依賴嘅右、下、右下三格已完成。

填表方向：

  dp[m][n] 係終點
  i: m → 0
  j: n → 0

dp[i][j] 依賴：
  dp[i+1][j+1]  WRONG / MATCH
  dp[i+1][j]    MISSING
  dp[i][j+1]    EXTRA

每格唔保存完整 result list，只保存：

Cell(
    score=Score(cost, match_count, non_normal_wrong_count),
    operation="MATCH|WRONG|MISSING|EXTRA|END",
    next_i=...,
    next_j=...,
    sub_type=...,
)

建議填表 pseudocode

m, n = len(correct), len(answer)
dp = matrix(m + 1, n + 1)
dp[m][n] = Cell(score=(0, 0, 0), operation="END")

for i from m down to 0:
    for j from n down to 0:
        if (i, j) == (m, n):
            continue

        candidates = []

        if i < m and j < n and correct[i] == answer[j]:
            candidates.append(MATCH + dp[i+1][j+1])
        else:
            if i < m and j < n:
                candidates.append(WRONG + dp[i+1][j+1])
            if i < m:
                candidates.append(MISSING + dp[i+1][j])
            if j < n:
                candidates.append(EXTRA + dp[i][j+1])

        dp[i][j] = min(candidates, key=ranking_key)

# reconstruction
i, j = 0, 0
result = []
while dp[i][j].operation != "END":
    result.append(make_result_item(dp[i][j], correct, answer, i, j))
    i, j = dp[i][j].next_i, dp[i][j].next_j

正式執行流程

  1. Normalize correct/user answer，驗證長度。
  2. 建立 score table 同 backpointer table。
  3. 初始化 dp[m][n]；table edge 自然只會有 MISSING 或 EXTRA candidate。
  4. 由右下至左上填表，每格按現有三層 ranking 選最佳 operation。
  5. 由 (0,0) 沿 backpointer 重建 result items。
  6. 將 score/result 包裝成目前 caller 預期嘅 dictionary。
  7. gen_answer_image() 繼續消費同一 output contract。

優點、代價及陷阱

面向評估
改動量中；要清楚分開 score calculation 同 result reconstruction。
時間O(mn)，每格最多比較三個固定 candidates。
空間O(mn) cells；每格只保存固定大小 metadata，唔複製完整 suffix result。
穩定性無 recursion depth、cache lifetime 或 mutable cached value 問題。
可測性可以分開測 ranking、table score、backpointer 同 final contract，適合長期維護。

6. 完整流程例子

正確答案：がっこう；用戶答案：かこう。

期望教學結果：

次序OperationCorrectUserSubtype
1WRONGがかDAKUTEN
2MISSINGっ——
3MATCHここ—
4MATCHうう—

總 score：

cost = 2
match_count = 2
non_normal_wrong_count = 1
ranking key = (2, -2, -1)

方案 A 點行

  1. solve(0,0) 見到 が／か mismatch，試 WRONG、MISSING、EXTRA。
  2. WRONG 進入 solve(1,1)；っ／こ mismatch，再試三路。
  3. MISSING 進入 solve(2,1)；こ／こ MATCH，再到 solve(3,2)；う／う MATCH，最後終點。
  4. 其他 branches 如再次需要 solve(2,1) 或其他已計 state，直接讀 cache。
  5. 各層按 ranking key 回傳最佳 suffix，最終組成上表結果。

方案 B 點行

  1. 先填 dp[4][3]=END，再填最底 row（剩餘 user chars 全部 EXTRA）及最右 column（剩餘 correct chars 全部 MISSING）。
  2. 倒序遇到 う／う、こ／こ，分別記錄 MATCH backpointer。
  3. 到 っ／こ 時，MISSING + 已知 dp[2][1] 會成為最佳候選。
  4. 到 が／か 時，WRONG subtype 係 DAKUTEN；加上後面最佳 score，成為 dp[0][0]。
  5. 由左上沿 backpointer 依次得到 WRONG → MISSING → MATCH → MATCH。
兩套方案應該得到完全相同嘅 public output。優化後如果 alignment 改咗，除非你刻意修改 tie-break 規則，否則應當作 regression。

8. 25 字上限應該點定位

你喺 quiz/forms.py:35 將 max_length 改成 25，作用係 request validation：

  • 阻止異常長 input 進入 service。
  • 限制 DP table 上限為 26 × 26 = 676 states（假設 correct answer 同樣受 25 字 domain rule）。
  • 令錯誤訊息及產品規則有清晰 boundary。

但仍要補兩點：

  1. Correct answer boundary：Vocab.kana model 上限仍係 255。如果 database kana 超過 25，user form 最多只能交 25，會變成永遠答唔完整。要決定係 vocab validation 限制 kana，定 compare service 對兩邊作明確 guard。
  2. Server-side service boundary：form 係目前 HTTP caller 嘅 guard，但 management command、test 或未來其他 caller 可以直接 call service。核心 function 最好仍對 input size 有明確 contract。
結論：25 字上限應保留，但定位係 defense-in-depth；真正解決速度問題仍然要做 memoization 或 DP。

9. 實作次序與驗收測試

實作前先鎖住行為

  • 完全相同：全部 MATCH，cost 0。
  • 單一普通錯字：WRONG/NORMAL。
  • 濁音、半濁音、小假名：保留各 subtype。
  • 頭、中、尾 missing／extra。
  • 多個 minimum-cost alignment：確認 match/subtype tie-break 同現在一致。
  • 空 correct、空 user、兩邊都空。

Performance tests

cases = [10, 15, 25]
for length in cases:
    correct = "あ" * length
    answer = "ん" * length
    assert compare(correct, answer) completes within project time budget

測試唔好只寫一個過分嚴格嘅毫秒數，因為 CI 機器速度會浮動。可以用寬鬆 budget 防止演算法退回指數級，例如 25 字 worst case 必須遠低於 1 秒；實際 threshold 要按本機及 CI 數據決定。

建議落地順序

  1. 將現有輸出案例變成 characterization tests。
  2. 選 A 或 B 實作，保持 compare_kana_answer() public contract。
  3. 跑 correctness tests，比較舊版同新版短輸入結果。
  4. 跑 worst-case benchmark，確認 25 字唔會出現 request stall。
  5. 補 correct-answer/domain length validation。
  6. 再經 browser 驗證 result images、missing／extra overlay data 無 regression。

10. 最終建議

以呢個 project 現況，我會揀 Bottom-up DP + backpointer。原因唔係 memoization 無效，而係 answer comparison 已經係一個有 domain-specific ranking、圖片輸出同日後測試需求嘅核心功能。DP 可以將「計最佳 score」同「產生 presentation result」清楚分開，之後擴充 subtype 或 debug alignment 都比較直接。

如果你想先用最少改動解除風險，memoization 仍然係合理方案；但應將 cached result 改成 immutable tuple，並視為過渡實作。
