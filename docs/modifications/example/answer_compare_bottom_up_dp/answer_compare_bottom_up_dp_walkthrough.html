Bottom-up DP 逐格圖解

用方案 B 重寫 QuizService.answer_compare() 時，個表點樣建立、每一格點揀、最後點樣還原答案。

例子：正確答案「がっこう」；用戶答案「かこう」。本文件係實作前教學，未修改 application code。

1. 先用一幅圖理解全流程

DP 先解決「每個位置開始，餘下部分最好點對齊」，之後先將選擇串成畫面需要嘅 result list。

2. 一格究竟代表乜

dp[i][j] 唔係只比較兩個字。佢代表：

由 correct 第 i 個字開始，同 user answer 第 j 個字開始，餘下兩段字串最佳嘅完整比較結果。

用今次例子：

StateCorrect suffixUser suffix問題
dp[0][0]がっこうかこう整條答案最好點比較？
dp[1][1]っこうこう處理完 が／か 後，餘下最好點比較？
dp[2][1]こうこう漏咗「っ」之後，餘下兩邊完全相同。
dp[4][3]空字串空字串兩邊都完成，cost 係 0。

因為 dp[i][j] 只依賴右邊、下面同右下三格，所以只要由右下填返去左上，每格需要嘅答案都已經存在。

3. 座標同三條路

MATCHWRONGMISSINGEXTRA

字符相同時，沿用你目前演算法：直接選 MATCH，唔需要再比較三路。字符唔同先建立 WRONG、MISSING、EXTRA candidates。

4. Score 唔係一個數字

每格保存三個數：

Score(
    cost,                     # edit 次數，越少越好
    match_count,              # MATCH 數，同 cost 時越多越好
    non_normal_wrong_count,   # 特殊錯誤 subtype 數，再同分時越多越好
)

實際排序要轉成全部「越細越好」：

ranking_key(score) = (
    score.cost,
    -score.match_count,
    -score.non_normal_wrong_count,
)
候選ScoreRanking key次序
A(2, 2, 1)(2, -2, -1)最佳
B(2, 2, 0)(2, -2, 0)第二
C(2, 1, 1)(2, -1, -1)第三
D(3, 3, 2)(3, -3, -2)cost 較高，最差

Cost 永遠係第一優先。特殊 subtype 唔會令系統接受更多錯誤，只會喺 edit cost 同 match 數都相同時決定 alignment。

5. 建立今次例子嘅矩陣

Correct 有 4 個字，user answer 有 3 個字；加埋「已行到尾」嘅 boundary，所以係 5 rows × 4 columns。

點解由右下開始，而唔係左上開始？

因為今次將 dp[i][j] 定義成「由目前位置開始，餘下兩段 suffix 最佳點比較」。要計目前格，就一定要先知道行完操作之後嘅 child：

右下角 dp[m][n] 係唯一一開始就知道答案嘅 state：兩邊 suffix 都係空，唔需要任何 edit，所以 score 必然係 (0,0,0)。由呢個已知答案向左、向上擴散，就可以逐步解出所有較長 suffix。

DP 唔係永遠只可以由右下開始。如果將 state 改成「prefix correct[:i] 同 answer[:j] 嘅最佳比較」，佢會依賴左、上、左上，咁就可以由左上填去右下。今次採用 suffix 定義，係因為同原本 recursive function 嘅 pos_of_correct／pos_of_user 思路完全一致。真正規則係：先計 dependency，再計依賴佢嘅格。

5A. 你問嘅三個問題：填表次序同最終路線其實係兩樣嘢

先修正一個容易誤會嘅地方：之前由 dp[4][3] → dp[3][2] → dp[2][1] 咁講，係展示「最後選中嗰條路嘅 dependency」，唔係 Python nested loop 真正逐格填表嘅先後次序。成張表一定會填晒；唔係只填圖中嗰幾格。

問題一：點解第一格係 dp[4][3]？

因為兩個數字係「已經消耗咗幾多個字」，唔係字符本身嘅最後 index：

字串長度未開始完全行完
Correct：がっこう4i=0i=4
User：かこう3j=0j=3

dp[4][3] 唔係因為程式「估」由尾開始比較；係因為佢代表兩邊都行完，答案最簡單而且肯定係 END。呢個係計其他格所需嘅基礎值。

問題二：dp[2][1] 之後點解唔係 dp[1][0]？

如果講真正填表 loop，dp[2][1] 之後其實亦唔係立即去 dp[1][1]。以下數字先係 nested loop 真正次序：

for i in range(4, -1, -1):       # 4, 3, 2, 1, 0
    for j in range(3, -1, -1):   # 3, 2, 1, 0
        fill dp[i][j]
填寫次序j=0j=1j=2j=3
i=0⑳⑲⑱⑰
i=1⑯⑮⑭⑬
i=2⑫⑪ dp[2][1]⑩⑨
i=3⑧⑦⑥⑤
i=4④③②① dp[4][3]

所以真正次序係：

... → dp[2][2] → dp[2][1] → dp[2][0]
    → dp[1][3] → dp[1][2] → dp[1][1] → dp[1][0]
    → dp[0][3] → dp[0][2] → dp[0][1] → dp[0][0]

dp[1][0] 當然會填，只係要先完成同一 row 嘅 dp[2][0]，然後下一 row 又由最右 j=3 開始。之前圖中 dp[2][1] → dp[1][1] → dp[0][0] 講緊嘅係最後答案反向依賴鏈，唔係 loop 次序。

問題三：點解 dp[0][0] 會用 dp[1][1]，唔係只用 dp[0][1]？

dp[0][0] 見到第一對字係「が」同「か」，兩字唔同，所以佢唔係預先決定只用其中一格；佢會同時比較三個可能嘅 child：

dp[0][1] 代表嘅唔係「自然下一格」，而係一個非常具體嘅假設：

將 user 第一個「か」當成 EXTRA 丟走
Correct 仍然停喺「が」      → i 仍然係 0
User 已經行到下一個「こ」  → j 變成 1
所以 child 係 dp[0][1]

呢條路有計，唔係被忽略；只係總 cost 3，高過 WRONG 路線嘅 cost 2，所以最後唔揀。相反，WRONG 會將「が／か」當成同一位置嘅濁音錯誤，兩邊一齊向前，因此 child 正確係 dp[1][1]。

一句分清楚：填表時會計晒 20 格；決定 dp[0][0] 時會比較三個 children；填完之後只沿勝出嘅 backpointer 路線輸出結果。呢三件事唔係同一個次序。

9. 第三步：沿 backpointer 重建 result

Reconstruction loop 唔再做任何選擇，只係讀已經決定好嘅 cell：

i, j = 0, 0
result = []

while cell[i][j].operation != END:
    result.append(operation_to_result_item(cell[i][j], i, j))
    i, j = cell[i][j].next_position

return {
    "cost": dp[0][0].score.cost,
    "match_count": dp[0][0].score.match_count,
    "non_normal_wrong_count": dp[0][0].score.special_count,
    "result": result,
}

11. 填表 pseudocode：逐段閱讀版

# A. 建立 table；每格最後保存一個 Cell
rows = len(correct) + 1
cols = len(answer) + 1
dp = [[None for j in range(cols)] for i in range(rows)]

# B. 右下角：兩邊都已完成
dp[m][n] = Cell(Score(0, 0, 0), END, None, None)

# C. 由最後一格倒序返去第一格
for i in range(m, -1, -1):
    for j in range(n, -1, -1):
        if i == m and j == n:
            continue

        candidates = []

        # D. 字符相同：沿用現有規則，直接 MATCH
        if i < m and j < n and correct[i] == answer[j]:
            child = dp[i + 1][j + 1]
            dp[i][j] = make_match_cell(child, i, j)
            continue

        # E. 字符不同／其中一邊到尾：建立合法 candidates
        if i < m and j < n:
            candidates.append(make_wrong_cell(dp[i+1][j+1], i, j))
        if i < m:
            candidates.append(make_missing_cell(dp[i+1][j], i, j))
        if j < n:
            candidates.append(make_extra_cell(dp[i][j+1], i, j))

        # F. 依 cost → match → subtype → candidate order 揀最佳
        dp[i][j] = min(candidates, key=ranking_key)

# G. 沿 dp[0][0] backpointer 產生 result list
return reconstruct(dp, correct, answer)
關鍵：loop 必須係 i=m...0、j=n...0。如果由左上開始填，dp[i+1][j] 等 child cells 仲未有答案。

12. 25 字限制下嘅實際成本

你已將 form answer 改成最多 25 字。當 correct answer 亦限制為最多 25 字：

項目最大值含義
Rows2625 個 correct chars + 終點
Columns2625 個 user chars + 終點
States676每格只計一次
每格 candidates最多 3固定工作量
Reconstruction最多 50 steps全 missing + 全 extra 嘅最長 alignment

呢個先係 DP 快嘅原因：輸入加長只會令矩陣面積按平方增加，唔會令 recursion tree 按三次方分枝爆炸。

13. 最容易寫錯嘅地方

  1. 只比較 cost：會遺失 match_count 同特殊 subtype tie-break，圖片 alignment 可能改變。
  2. 改變 candidate order：三個 ranking values 完全相同時，現有 Python min() 依靠 WRONG、MISSING、EXTRA list order 作最後決定。
  3. 填表方向倒轉：左上開始會讀到仍然係 None 嘅 child cells。
  4. 每格保存完整 result list：仍然會製造大量 list copying；Cell 應保存 backpointer。
  5. 重建時 index 用錯：MISSING 只有 correct char；EXTRA 只有 user char；MATCH/WRONG 兩邊都有。
  6. 只限制 form answer：Vocab.kana 仍可長達 255；要另外決定 correct answer domain boundary。
