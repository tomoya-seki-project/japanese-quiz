Email Activation Token 方案比較

比較方案 A「用 database model 保存 token」同方案 B「用 Django stateless token generator」，包括大約做法、優缺點、安全風險、password reset 配合方式，以及 Japanese Quiz project 適合採用邊一種。

核心分別

方案 ADatabase token model

先產生一個隨機 token，再將 token 或其 hash、到期時間及使用狀態保存落 database。驗證時查 database record。

心智模型：token 係一張由系統發出、可以追蹤同撤銷嘅票。

方案 BDjango token generator

系統用 user 狀態、timestamp、secret key 計算 token；database 唔保存 token。驗證時用相同資料重新計算及比較。

心智模型：token 係一個可以驗證真偽、但唔需要保存嘅簽章。

方案 A：建立 Database Token Model

大約流程

註冊建立 inactive user
→
產生 token使用安全隨機值
→
保存 recordhash、期限、狀態
→
寄出 linkemail 帶原始 token
→
查詢及啟用驗證後標記 used

概念 schema

class EmailActivationToken(models.Model):
    user = models.OneToOneField(...)
    token_hash = models.CharField(max_length=64, unique=True)
    expires_at = models.DateTimeField()
    used_at = models.DateTimeField(null=True, blank=True)
    created_at = models.DateTimeField(auto_now_add=True)

Email 放原始 token，database 建議只保存 token hash。若 database 洩漏，攻擊者唔可以直接將儲存值當 activation link 使用。

好處

  • 可以精確記錄建立、到期、使用及撤銷狀態。
  • 可以由 Admin 或後台單獨撤銷某條 token。
  • 容易設定 activation 與 password reset 各自期限。
  • 容易統計 resend 次數、失敗次數及保留 audit trail。
  • 需要同時管理多部裝置、多條 token 時彈性較高。

壞處

  • 需要新增 model、migration、query 及定期清理過期 records。
  • 要自行處理 token collision、重用、race condition及撤銷。
  • 若保存 plaintext token，database 洩漏會直接洩漏有效連結。
  • 需要清楚定義 resend 係覆蓋舊 token，定容許多條並存。
  • 簡單一次性 activation 可能出現不必要嘅狀態複雜度。

適合情況

  • 有完整 audit／合規要求。
  • 管理員要查閱、撤銷或重新發出指定 token。
  • 每種 token 需要獨立期限、用途及狀態。
  • 需要記錄每一次寄送及使用結果，而唔只係帳戶最終狀態。

方案 B：Django Stateless Token Generator

大約流程

註冊建立 inactive user
→
計算 tokenuser 狀態＋時間＋secret
→
寄出 linkuidb64＋token
→
重新計算檢查簽章及期限
→
啟用is_active=True

概念 generator

class AccountActivationTokenGenerator(PasswordResetTokenGenerator):
    def _make_hash_value(self, user, timestamp):
        return f"{user.pk}{timestamp}{user.is_active}{user.email}"

account_activation_token = AccountActivationTokenGenerator()

is_active 參與 token 計算後，成功啟用帳戶會改變計算結果，舊 activation link因而失效。

好處

  • 不需要新增 token model 或 migration。
  • 不需要保存及清理大量過期 token records。
  • database 冇 plaintext token 可被直接偷取。
  • 建基於 Django成熟嘅 token生成及時間驗證方式。
  • 對「註冊後一次性啟用」流程較精簡。

壞處

  • 無法直接列出系統曾經發出過邊幾條 token。
  • 無法只撤銷一條指定 token；要改變 user相關狀態令 token失效。
  • 唔會自然提供寄送次數、使用時間或 audit history。
  • 直接繼承時通常使用 PASSWORD_RESET_TIMEOUT，activation與 reset可能共用期限。
  • 自訂 _make_hash_value() 時要小心選擇令 token失效嘅欄位。

適合情況

  • 一般網站嘅一次性 email activation。
  • 唔需要逐條 token audit或手動撤銷。
  • 希望減少 database狀態及維護成本。
  • 已經採用 Django authentication框架及內建 password reset。

完整比較

比較項目方案 A：Database model方案 B：Token generator
Token 儲存保存 record；建議只存 hash不保存 token
Database migration需要不需要
過期資料清理需要清理或保留作 audit不需要
單條撤銷容易較困難
Audit trail容易建立要靠額外 event/log model
獨立有效期限直接用 expires_at預設可能共用 PASSWORD_RESET_TIMEOUT
安全實作成本較高，要自行處理完整生命週期較低，但仍需正確自訂 hash value
Resend要決定覆蓋或多條並存可重新寄出；user狀態不變時 token可能相同或隨時間改變
適合規模複雜 workflow、audit、合規簡單一次性 activation

如果之後加入 Password Reset

Password reset 本身唔構成建立 token model嘅理由。Django已經提供完整 password-reset views、forms及 default_token_generator。

Email activation

使用自訂 AccountActivationTokenGenerator，將 is_active 加入 hash value。帳戶啟用後，舊 link自然失效。

Password reset

使用 Django內建 default_token_generator。密碼成功改變後，舊 reset link自然失效。

唔建議同一個自訂 generator處理兩種用途。Activation關心 is_active；password reset關心 password及登入狀態。兩者應該使用不同 generator及不同 URL。

如果 activation需要24小時，而 password reset只需要30分鐘，stateless方案就要加入用途專屬 timeout處理；database方案則可直接為每條 record設定 expires_at。

Japanese Quiz Project 建議

目前建議使用方案 B。現階段需求係 public registration建立 is_active=False user，完成一次 email activation後改成 True。未見逐條撤銷、完整 audit或同時管理多條 token嘅需要，因此新增 token table帶來嘅狀態成本大過收益。

建議組合

  1. Email activation使用專用 AccountActivationTokenGenerator。
  2. Password reset使用 Django內建 default_token_generator及相關 views。
  3. 兩種功能使用不同 URL、template及 email內容。
  4. 第一版可共同使用24小時期限；需要不同期限時再獨立處理。
  5. Activation完成後先執行 UserVocabService.sync_vocab_safely()。

幾時應該轉用方案 A？

當需求明確加入逐封寄信追蹤、管理員撤銷、合規 audit、多 token並存或用途專屬生命週期時，再引入 database token model。唔應該只因為將來可能需要而預先增加狀態。

兩種方案都要守嘅安全檢查表

  • Public registration必須明確建立 is_active=False user。
  • 使用 HTTPS，避免 token喺傳輸途中被截取。
  • Log唔可以記錄完整 token、完整 activation URL或密碼。
  • 成功啟用後 token必須不可重用。
  • 處理過期、格式錯誤、user不存在及已啟用狀態。
  • Resend回應唔應該洩漏某個 email有冇註冊。
  • Resend加入 cooldown或 rate limit，防止濫發 email。
  • 寄信最好喺 database transaction成功 commit之後執行。
  • Activation成功後先做 vocab sync；sync失敗唔應該取消已完成嘅 activation。
  • 為正常、過期、錯誤、重用、resend及登入限制建立 automated tests。

避免直接複製舊教學 signal。每次 user save都重新產生 token會令修改資料、改密碼、Admin保存甚至 activation本身意外換 token。Token建立及寄信應由明確嘅 registration／resend流程負責。
