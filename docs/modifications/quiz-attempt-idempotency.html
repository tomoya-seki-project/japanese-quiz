QuizAttempt 防止重複答題與並行更新修改報告

修改摘要 核心流程已完成

修改前，Quiz 主要以 session 入面嘅 question_user_vocab_id 判斷目前題目； Answer 或 Skip 一到達 server，就直接修改 UserVocab。如果同一個表單因 double click、 多個 tab 或網絡重試而同時送出兩次，兩個 request 都有機會讀到相同舊狀態，繼而重複更新 weight、streak、答題次數與 session 統計。

修改後，每次出題都建立一筆帶唯一 UUID token 嘅 QuizAttempt。Answer 與 Skip 會喺同一個 database transaction 入面先鎖定 attempt，再鎖定該 user 嘅 UserVocab； 只有仍為 PENDING 嘅 attempt 可以完成一次狀態轉換。舊 token、重複 request、失效題目 同不完整 session 會得到不同處理，避免第二個 request 錯誤結束新一題或重複計分。

  1. 以持久化 QuizAttempt 取代只靠 session 判斷一次性操作。
  2. 用 transaction.atomic() 將 vocab 更新與 attempt 狀態轉換綁成一個單位。
  3. 用 select_for_update() 排隊處理同一 attempt，並以 of=("self",) 收窄 UserVocab lock。
  4. Answer、Skip、下一題及 unfinished resume 全部傳遞同一題嘅 attempt token。
  5. 前端 in-flight guard 減少 double click；後端狀態與 row lock 先係最終保障。

修改目的／理由

UserVocab 代表 user 長期持有嘅學習資料，唔代表「今次畫面顯示緊嘅呢一題」。 新增 QuizAttempt 後，每次出題都有獨立 token 同生命週期，server 可以分辨目前題目、 舊頁面提交，以及已經完成嘅 request。

前後差異與運作解釋

UUID token 唔係答案內容，亦唔係授權本身；佢係一次出題嘅不可預測識別值。Service 查詢時仍同時限制 user=user，所以其他 user 即使得到 token 都唔可以處理該 attempt。資料庫嘅 unique=True 令兩個 attempts 唔會共用同一 token。

初次出題、Next 及 unfinished resume 都會保存 question_attempt_token。Answer form 同 Skip form 使用同一 token，代表兩種動作競爭同一個 PENDING 狀態，而唔係各自有一次處理機會。

新使用技術

Django 6.0.5 嘅 models.UUIDField 負責 model 欄位；Python 標準庫 uuid.uuid4 產生預設值；forms.UUIDField 會喺 View 執行前先將字串轉成 UUID， 格式錯誤會進入既有 form-invalid JSON contract。

目的二：將 Answer／Skip 變成一次性原子操作

修改目的／理由

單純先讀 status、後寫 status 仍有 race condition：兩個 request 可以同時讀到 PENDING。新 service 將讀取、驗證、修改 UserVocab、更新 attempt 狀態放入同一 transaction，並先鎖 attempt row。後到嘅 request 需要等待；取得 lock 後會讀到 ANSWERED 或 SKIPPED，因而回傳 already_processed。

受影響檔案與責任

檔案／symbol責任
quiz/service/quiz.py · process_answer_attempt()原子判答、更新 UserVocab、將 attempt 完成為 ANSWERED。
quiz/service/quiz.py · process_skip_attempt()原子執行 skip punishment、將 attempt 完成為 SKIPPED。
quiz/service/quiz.py · skip_question_punish()直接操作已鎖定 instance，避免再次查詢及脫離 lock 對象。

修改後：先鎖 attempt，再鎖 UserVocab

quiz/service/quiz.py · process_skip_attempt() · line 108

@staticmethod
@transaction.atomic
def process_skip_attempt(*, user, attempt_token):
    quiz_attempt = (
        QuizAttempt.objects
        .select_for_update()
        .get(user=user, token=attempt_token)
    )

    if quiz_attempt.status != QuizAttempt.Status.PENDING:
        return False, "already_processed"

    skipped_user_vocab = (
        UserVocab.objects
        .select_for_update(of=("self",))
        .filter(
            user=user,
            pk=quiz_attempt.user_vocab_id,
            in_use=True,
            vocab__is_active=True,
        )
        .first()
    )

    QuizService.skip_question_punish(
        skipped_user_vocab=skipped_user_vocab
    )
    quiz_attempt.status = QuizAttempt.Status.SKIPPED
    quiz_attempt.processed_at = timezone.now()
    quiz_attempt.save(...)
    return True, None

前後差異與運作解釋

  1. @transaction.atomic 開始 transaction。
  2. 先以 user + token 查 attempt，並用 FOR UPDATE 鎖 row。
  3. 只接受 PENDING；已處理 attempt 唔再改任何學習資料。
  4. 再鎖 attempt 指向嘅 UserVocab，並重新確認 in_use 與 vocab.is_active。
  5. 修改學習統計後，將 attempt 轉成 ANSWERED／SKIPPED 並填寫 processed_at。
  6. method 正常結束就 commit；發生未捕捉 exception 時，兩組更新一齊 rollback。
鎖順序係設計一部分：Answer 同 Skip 都固定先鎖 QuizAttempt、再鎖 UserVocab。 如果兩條路使用相反次序，會增加 deadlock 風險。

of=("self",) 點解重要

UserVocab query 會因 vocab__is_active 及 select_related("vocab") 涉及共用 Vocab table。唔限制 FOR UPDATE 目標時，相關 row 亦可能被納入鎖定範圍。 兩個不同 users 即使只更新各自 UserVocab，都可能因為指向同一 Vocab 而不必要地排隊。 

User A ─ UserVocab A ─┐
                      ├─ 共用 Vocab「学校」
User B ─ UserVocab B ─┘

select_for_update(of=("self",)) 入面嘅 self 唔係 Python method 嘅 self，而係 Django QuerySet 用嚟表示「主要 model」嘅特殊名稱；此處即只鎖 UserVocab。Query 仍可讀取及篩選 Vocab，但唔需要鎖共用字典資料。

新使用技術

Django 6.0.5 嘅 transaction.atomic 提供 transaction boundary； QuerySet.select_for_update() 產生 PostgreSQL row-level lock。實際環境為 PostgreSQL 16.15， Django connection 已確認 has_select_for_update=True 與 has_select_for_update_of=True。

目的三：分清 session、POST 與 database 各自責任

修改目的／理由

session 仍負責描述 browser 目前應顯示邊題，但資料庫 attempt 先係一次性更新嘅權威來源。 POST 中嘅 vocab ID 與 token 會先同 session 比較，提供即時 stale-page feedback；真正修改時， service 由 attempt token 反查 user_vocab_id，唔信任 browser 指定更新目標。

Service failure 唔再全部當成同一件事：

Reason意思View 行為
already_processed同一 attempt 已被 Answer 或 Skip 完成。回傳 HTTP 409；唔清 session，避免舊 request 終止新題。

Django class-based FormView 同自訂 QuizAjaxFormMixin 合作：UUID 格式錯誤由 form validation 回傳 400；格式正確但狀態衝突由 service 判斷，再以 HTTP 409 表達 conflict。

目的四：前端減少同一畫面重複送出

修改目的／理由

Database 保護係最後防線，但 browser 可以先避免普通 double click 產生第二個 request。 on_handling 係目前 quiz area handler 嘅 in-memory 狀態；request 未完成時，之後嘅 submit event 會直接返回，完成或失敗後由 finally() 重開操作。

前後差異與運作解釋

flag 放喺 quizAreaHandler() closure，Answer 與 Skip 共用同一個 guard，所以 Answer request 未完成時亦唔可以同時按 Skip。finally() 無論 success、server-reported error 或 network error 都會執行，避免一次錯誤後永久鎖死介面。

新使用技術

呢部分使用既有 Fetch Promise chain 嘅 finally()；無新增第三方前端 library。 此 guard 只保護目前 JavaScript execution context，唔能夠處理另一個 tab、重試工具或直接 HTTP request， 因此唔可以取代 backend attempt status 與 row lock。

整體運作改變

出題
  │
  ├─ 建立 QuizAttempt(PENDING, UUID token)
  ├─ session 保存 question_user_vocab_id + question_attempt_token
  └─ Answer／Skip forms 收到同一 token

提交 Answer 或 Skip
  │
  ├─ 前端：已有 request in flight？── 是 → 忽略第二次 submit
  │
  └─ 後端：form 驗證 UUID
       │
       ├─ session 無題目／無 token → no-question 或 invalid-session response
       ├─ POST identity 與 session 不符 → stale response
       └─ identity 符合
            │
            └─ transaction.atomic
                 ├─ lock QuizAttempt
                 ├─ status 非 PENDING → 409 already_processed
                 ├─ lock UserVocab only（of="self"）
                 ├─ 更新學習狀態
                 └─ attempt → ANSWERED／SKIPPED + processed_at

成功 response
  └─ 清除目前 question ID/token；Next 時建立新 attempt

最關鍵嘅轉變係「先認題，再改資料」：以前 browser 傳入嘅 vocab ID 直接決定更新目標；而家 token 先定位 database attempt，再由 attempt 決定 UserVocab。session check 主要改善 user experience，database transaction 先維持資料一致性。

已知限制與後續建議

  • 未有真正雙 connection concurrency automated test：目前驗證咗 PostgreSQL lock SQL、transaction flow 同重複 token sequential behavior；正式 tests 應使用 TransactionTestCase 或等效多 connection 測試。
  • test database 權限：目前 PostgreSQL application user 無法建立 test database；可另設 test DB、預先建立 test database，或只喺受控開發環境授予適當權限。
  • PENDING retention：user 關閉頁面後，未完成 attempts 可能長期保留。呢個唔影響一次性處理，但日後需要 scheduled cleanup／retention policy。
  • failure reason 使用字串："already_processed" 等值目前由 tuple 傳遞；規模增加時可考慮 Enum 或 dataclass result，減少拼字錯誤及 tuple 次序負擔。
  • 前端 guard 範圍：on_handling 只涵蓋同一頁面；backend lock 仍然不可移除。
