由 SQLite 轉用 PostgreSQL：Django database backend、環境設定與 schema 重建

核心轉換已完成

修改概要

專案原本由 Django 直接開啟 repository 根目錄嘅 db.sqlite3。今次改動安裝 PostgreSQL server 與 Psycopg 3，將 Django DATABASES backend 改成 PostgreSQL，再以 python-dotenv 從本機 .env 載入連線資料。新 PostgreSQL database 透過既有 Django migrations 重建 schema，而唔係沿用 SQLite database file。

現場驗證確認 PostgreSQL 16 cluster online、Django 實際連線 vendor 為 postgresql、24 個 tables 可被 introspect，而且所有 migrations 已套用。Users、categories 同 vocabs 均已有資料。目前 application role 有 LOGIN、冇 CREATEDB、亦唔係 superuser；所以可以使用已存在嘅 application database，但完整 test suite 喺建立獨立 test database 前被拒絕。

主要修改重點

  • Database engine 由 SQLite file backend 改為 Django PostgreSQL backend。
  • 加入 Psycopg 3.3.5，負責 Django／Python 與 PostgreSQL 之間嘅 database protocol。
  • 加入 python-dotenv 1.2.3，以環境變數提供五項 database connection settings。
  • 用現有 migrations 喺全新 database 重建 schema，再重新建立 user 及匯入基礎 vocab data。
  • 分清 CREATE USER／CREATE ROLE、database ownership 同 CREATEDB 權限。

修改目的 1：由 SQLite file backend 轉到 PostgreSQL

修改目的／理由

SQLite 將 database 保存成單一檔案，適合 project 起步；今次目標係令 development runtime 真正使用獨立 PostgreSQL server。Django ORM 同 models 繼續保留，改動集中喺 database adapter、connection settings 同外部 server。

受影響檔案與責任

  • config/settings.py:88：選擇 Django database backend，並提供連線參數。
  • requirements.txt:3：宣告 runtime 需要 Psycopg。
  • requirements-dev.txt:4：記錄目前 development environment 安裝版本。
  • docs/modifications/postgreSQL.html：記錄 PostgreSQL 安裝、role／database 建立及連線步驟；佢係操作來源，唔係本報告嘅 Git baseline。

修改前

config/settings.py，HEAD baseline

DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.sqlite3',
        'NAME': BASE_DIR / 'db.sqlite3',
    }
}

Python process 直接讀寫 project 根目錄嘅 SQLite file，唔需要另外嘅 database server 或 driver。

修改後

config/settings.py:88，working tree

DATABASES = {
    'default': {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": os.environ["DB_NAME"],
        "USER": os.environ["DB_USER"],
        "PASSWORD": os.environ["DB_PASSWORD"],
        "HOST": os.environ["DB_HOST"],
        "PORT": os.environ["DB_PORT"],
    }
}

requirements.txt:3

psycopg==3.3.5
psycopg-binary==3.3.5

前後差異與運作解釋

ENGINE 決定 Django 使用邊個 backend implementation。改成 django.db.backends.postgresql 後，ORM 仍然產生 queries，但實際 connection、SQL adaptation、transactions 同 database-specific behavior 會由 PostgreSQL backend 配合 Psycopg 處理。

psycopg 係 import 得到嘅 Python package；psycopg-binary 提供預先編譯嘅 binary implementation。原教學使用 pip install "psycopg[binary]"，而現時 freeze 結果將兩個 distribution 分開列出。兩者同時出現唔代表 application 需要 import 兩套 driver。

舊 SQLite block 目前以註解形式保留喺新設定上方，只作短期對照；runtime 唔會執行註解內容，亦唔會再開啟 db.sqlite3。

新使用技術

PostgreSQL 16 係獨立 relational database server。現場檢查顯示本機 16/main cluster 喺 port 5432 online，client 版本為 16.15。

Psycopg 3.3.5 係 Python PostgreSQL adapter，將 Django backend 嘅 connection request 同 parameters 交畀 PostgreSQL。Django 6.0 要求 Psycopg 3.1.12 或以上，因此目前版本符合 framework requirement。

修改目的 2：將 database credentials 移出 settings

修改目的／理由

PostgreSQL connection 需要 database name、role、password、host 同 port。如果將真實值直接寫入 tracked settings.py，Git history 會保存 credentials。今次改為由本機 .env 提供值，而 application code 只保留變數名稱。

受影響檔案與責任

  • config/settings.py:13：匯入 os 同 load_dotenv。
  • config/settings.py:22：指定 project root 下嘅 .env。
  • .gitignore:5：阻止真實 .env 進入 Git。
  • .env.example：提供五個必要變數嘅可分享結構；本報告刻意唔讀取或展示任何真實 credential value。
  • requirements.txt:5：宣告 python-dotenv 1.2.3。

修改前

config/settings.py／.gitignore，HEAD baseline

from pathlib import Path

BASE_DIR = Path(__file__).resolve().parent.parent
__pycache__/
db.sqlite3
.vscode/
.venv/

SQLite connection 只需要 file path，所以未有 database credential loader，亦未有 .env ignore rule。

修改後

config/settings.py:13、.gitignore:5，working tree

import os

from dotenv import load_dotenv

load_dotenv(BASE_DIR / ".env")
.env

.env.example，新增而未 tracked；values 已刻意遮蔽

DB_NAME=<example-value>
DB_USER=<example-value>
DB_PASSWORD=<example-value>
DB_HOST=<example-value>
DB_PORT=<example-value>

前後差異與運作解釋

Django import settings module 時會先呼叫 load_dotenv(BASE_DIR / ".env")，將檔案內嘅 key/value 加入 os.environ。之後 DATABASES 用方括號讀取五個 keys；任何必要 key 缺少時會立即拋出 KeyError，避免 application 靜默連去錯誤 database。

load_dotenv() 預設 override=False，所以 deployment environment 已經提供同名變數時，系統環境值優先，local .env 唔會覆蓋佢。呢個 behavior 令同一份 settings 可以同時服務 local development 同外部 secret injection。

.gitignore 只影響未 tracked files，亦唔會加密 .env。如果 secret 曾經 commit，之後加入 ignore rule 並唔會由 history 移除佢。現場 git check-ignore 已確認根目錄 .env 由新規則排除。

新使用技術

python-dotenv 1.2.3 將 dotenv file 解析成 process environment variables。呢次只用佢做 local configuration bootstrap；真正讀值仍然係 Python standard library os.environ。

.env.example pattern 將「需要邊啲 keys」同「真實 secrets」分開。Example file 應 commit，真實 .env 應保持 ignored；兩者責任唔可以調轉。

修改目的 3：喺新 database 重建 schema 與基礎資料

修改目的／理由

改 backend 只會令 Django 指向另一個 database，唔會自動將 SQLite tables 或 records 搬過去。原操作紀錄選擇將 PostgreSQL 視為全新 database：先重播現有 migrations 建立 schema，再重新建立 admin user，同以 project import command 補回 vocab／category 基礎資料。

受影響檔案與責任

  • */migrations/*.py：既有 schema 歷史，今次冇因轉 backend 而另寫一批 PostgreSQL table definitions。
  • manage.py migrate：將 migration graph 套用到全新 PostgreSQL database。
  • dictionary/management/commands/import_vocab.py：現有 vocab import 入口。
  • docs/modifications/postgreSQL.html：記錄 migrate、showmigrations、vendor check、createsuperuser 同重新匯入基礎資料嘅實際流程。

修改前

原本 database state

Django ORM
    ↓
SQLite backend
    ↓
db.sqlite3（schema + records）

Schema 同 data 都存在同一個 SQLite file。更改 settings 唔會令呢個 file 內容自動出現喺 PostgreSQL。

修改後

docs/modifications/postgreSQL.html 所記錄嘅 operational flow

python manage.py shell -c \
"from django.db import connection; print(connection.vendor)"
python manage.py createsuperuser
python manage.py import_vocab ...

新 PostgreSQL database 由 migrations 建 schema，再以明確命令建立或匯入所需 data。

前後差異與運作解釋

migrate 讀取每個 app 嘅 migration files，依 dependency order 建立 tables、constraints、indexes 同 Django metadata。佢搬嘅係schema history，唔係 SQLite records。原紀錄明確選擇不做 SQLite data dump／load，因此舊 user 同 application records唔會自動保留。

現場檢查顯示所有列出 migrations 均為 [X]，包括 working tree 新增嘅 quiz.0001_create_quiz_attempt；database introspection 可見 24 個 tables。只讀存在性檢查亦確認目前 database 有 users、categories 同 vocabs，但唔會由結果推斷每筆內容、數量或者同舊 SQLite 完全相同。

新使用技術

Django migration replay 係跨 database 重建 schema 嘅既有 framework 能力。Models 表達 project schema，migration files 表達有次序嘅演進；針對新 database 執行全部 migrations，唔等於要因轉換 engine 再執行 makemigrations。

Django connection introspection 用 backend-neutral API 列出目前 database tables；connection.vendor 則提供實際 backend identifier，避免只睇 settings 字串就聲稱 connection 成功。

修改目的 4：理解 role 與 test database 權限

修改目的／理由

網站可以連線及執行 migrations，但 manage.py test 仍然可能報 permission denied to create database。原因係 PostgreSQL 將「登入」、「擁有／操作某個既有 database」同「建立另一個 database」分成不同權限；application 運作成功唔代表 test runner 自動具有建立 database 嘅權限。

受影響檔案與責任

  • docs/modifications/postgreSQL.html：記錄以 CREATE USER 建立 application role，再由 administrator 建立及指定 application database owner。
  • PostgreSQL cluster role attributes：屬外部 database server 狀態，唔存在於 Django code 或 migrations。
  • Django test runner：測試開始前嘗試建立獨立 test database，完成後再銷毀，避免接觸 application data。

目前建立方式與預設權限

docs/modifications/postgreSQL.html，password 已遮蔽

CREATE USER japanese_quiz_app
WITH PASSWORD '<redacted>';

CREATE DATABASE japanese_quiz
OWNER japanese_quiz_app;

CREATE USER 等同 CREATE ROLE ... LOGIN。由於冇明確寫 CREATEDB，新 role 預設係 NOCREATEDB。

等價寫法與權限切換

PostgreSQL role commands；只作說明，本報告冇執行

-- 等價嘅 application login role
CREATE ROLE japanese_quiz_app
WITH LOGIN PASSWORD '<redacted>';

-- Local development：容許 Django 建 test database
ALTER ROLE japanese_quiz_app CREATEDB;

-- 收回建立 database 權限
ALTER ROLE japanese_quiz_app NOCREATEDB;

前後差異與運作解釋

概念代表意思目前狀態／影響
CREATE USERCREATE ROLE 嘅別名，但預設加上 LOGINApplication role 可以作為 connection user 登入
CREATE ROLE建立 cluster-level role；未指定時預設 NOLOGIN如要直接登入，必須明確加 LOGIN
OWNER japanese_quiz_app令 role 擁有指定嘅既有 application database可以喺 japanese_quiz 建 tables、執行 migrations；唔會因此取得 cluster-level CREATEDB
CREATEDB容許 role 建立新 databaseDjango test runner 建立獨立 test database 時需要
NOCREATEDB禁止 role 建立新 database，而且係預設值網站仍可使用已獲授權嘅 database，但 tests 無法自行建立 test database

今次 database 本身係由 postgres administrator 執行 CREATE DATABASE，再用 OWNER 將指定 database 交畀 application role。因此 application role 冇 CREATEDB 都可以正常使用 japanese_quiz。Django tests 則預設另建一個 test database，所以權限邊界喺呢一步先顯現。

如果呢個係只供本機開發嘅 role，可以由 administrator 暫時或持續授予 CREATEDB，再執行 tests。完成後使用 ALTER ROLE japanese_quiz_app NOCREATEDB; 會收回權限；一旦收回，下次 test runner 再要建立 database 時亦會再次失敗。Production application role 建議保持 NOCREATEDB，CI／tests 使用獨立 cluster 或 test role。

新使用技術

PostgreSQL unified role model 將傳統「user」同「group」統一成 role；有 LOGIN 嘅 role 先可以作為初始 connection identity。CREATE USER 只係提供預設 LOGIN 嘅方便語法，唔會順便授予 CREATEDB、CREATEROLE 或 superuser。

ALTER ROLE 可以喺 role 建立後改 attributes。CREATEDB／NOCREATEDB 係 cluster-level capability，唔應同某個 database 嘅 ownership 或 table privileges 混為一談。

  • 外部 server 建立步驟不可由 Git 還原：PostgreSQL package、cluster、role 同 database 屬本機狀態。現時有操作 HTML 紀錄，但未有 Docker Compose 或其他 infrastructure-as-code 自動重建。
